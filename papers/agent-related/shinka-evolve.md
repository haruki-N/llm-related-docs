## ShinkaEvolve: Towards Open-Ended And Sample-Efficient Program Evolution

**Abst**

- ShinkaEvolve: 化学的発見を高速・高精度に行うことを目的とした、LLM を使ったフレームワークで、オープンソース化されている
    - 従来のコード発展手法はサンプル効率が悪い（数千サンプル）上、クローズドソースだった
- 3つの新規性
    - Parent sampling technique: 探索と活用のバランスを取る手法
    - Code novelty rejection-sampling: 探索空間を効率的に巡るための新規性フィルタ
    - Bandit-based LLM ensemble selection strategy: 複数の LLM 候補から最適なものを動的に選ぶ戦略
- 貢献: ShinkaEvolve は広範な応用が可能で、サンプル効率に優れ、オープンソース化・コスト低減によって多様な計算問題へのオープンエンドな探索を民主化する

**Intro**

- LLM の進化に伴い、実験や仮説検証を自動で行う Agentic system などによって科学的な新しい発見が後押しされている
    - 競プロ、数理最適化、自動化エージェンティックデザインなど応用先は多岐にわたる
    - ただこれまでの提案手法は現実的な難しさを抱えている
        - サンプル効率が悪く、数千サンプル必要とするなど計算量や必要時間の観点でとても非効率
        - ほとんどがオープンソース化されていないので民主化や改善が進まない
- 提案・貢献
    1. ShinkaEvolve の導入: `parent program sampling srategy` と `code novelty rejection-sampling` よび `Bandit-based LLM samplint` の3つの新規アプローチを導入したフレームワークを提案
    2. 数理最適化 (circle packing), Agentic design (AIME tasks), 競プロ (ALE-Bench), LLM 訓練デザイン (MoE load balancing loss) の4つで ShinkaEvolve の性能を検証 → 人間の性能を超えるものが提案されたことを検証
    3. Apache 2.0 license として OSS 化

**Method**

- アルゴリズム概要: 3つのフェーズでフロー管理
    1. Parent and inspiration sampling
    2. Program mutation
    3. Program execution and world feedback

※ 進化的アルゴリズムにおけるアイランドモデル (Island Model) という手法が主題

- 用語の整理
    - 島: 独立した個体の集団（個体はここではプログラムなど LLM の出力と考えるとよさそう）
        - 個体のことをサブプログラムと呼ぶ
        - 一定のルールで個体を別の島に移行することで、進化の停滞（局所解にハマる状態）からの脱出や多様な進化を図る
        - 各島が独立するので、異なる探索経路を歩む
        - 島ごとに並列実行が可能なのでスケーラビリティもある
    - アーカイブ: 「過去に評価された全プログラム」を保存する DB
        - 島は自分のサブプログラムだけでなく、アーカイブからも情報を取り込む
        - Parent: 現在の島内で最良の個体やランダムに選んだ個体
        - インスピレーション: アーカイブ上位 or ランダム k 個
        - 突然変異 (Mutation): プログラムにおける演算子や if-else 条件、定数などをランダムに入れ替えたりすること。ShinkaEvolve では LLM に与える入力コンテキストでこれを実現

**Method1: Parent and inspiration sampling**

- ShinkaEvolve では固定サイズのアーカイブを持ち、評価スコアやメタ情報も保存
- Mutation context: 突然変異を促すため、Parent プログラムだけでなく、アーカイブから取得した最良/ランダムサンプル個体の inspiration プログラムを織り交ぜて LLM に入力
- ShinkaEvolve ではアイランドモデルを採用し、初期プログラムから複数島に展開して進化を図る
    - 島はパラレルに進化
- 各個体は時折別の島に移る migration を実行 → 全体としてより良い解を探索することが目的
    - 島の固有性を守るため、最良の個体は移動させない
    - サンプリングは階層的に実施する
        - アーカイブから島 ID を均一にサンプル → この ID が parent と inspiration の起点になる
        - ランダムサンプルとtop-kサンプルの両方を実施

探索と活用のバランス (parent プログラム選択) → 2つのサンプリング手法

- パワーロー (power law) サンプリング
    - 適応度スコアによるランク (r_i: r_i=1 is the best) を使った累乗サンプリングでサンプリング分布をつくる
    - αをハイパラとして、α=0 なら均等サンプリング、α→∞ならヒルクライミング (最良個体のみ)
- 重み付きサンプリング
    - フィットネススコアと「子孫数」を組み合わせて、シグモイドとフィットネススコアの中央値によるサンプリングを実施
- この2つのサンプリング手法によって「探索=新しい領域」と「活用=既知の良い解を再利用」のバランスが取れる

**Method2: Program mutation and novelty assessment**

- 新しいプログラムを作成する際、ShinkaEvolve ではLLMとそのハイパラセットのサンプリングから始まる
    - LLM としてさまざまな API provider をサポート
    - モデルをサンプルしたら、3つの突然変異アプローチを採用して、LLM の生成プログラムがより多様でクリエイティブになるようにする
        1. Diff-based Edits: 先行研究(AlphaEvolve)で提案された diff edits を採用 → 修正対象箇所に対して SEARCH/REPLACE ブロックを使う
        2. Full rewrites: 柔軟性を重視して、プログラム全体の書き換えも許可 → non-mutable なブロックは LLM による rewrite process で変わらないようにプログラムで担保
        3. Crossover Mutation: アーカイブのプログラムを組み合わせることで、crossover な突然変異を狙う
- AlphaEvolve にならい、text markers を使用 (`EVOLVE-BLOCK-START & EVOLVE-BLOCK-END` )
    - これによって、変更不可能なコードブロックをそのまま残しておける
    - コード変更提案を LLM から受け取った後、変更不可能なコードブロックが変わっていないことと、変更可能部分のパッチが有効であることを検証 → invalid なら Reflexion でフィードバック

Program Diversity via Novelty Rejection Smpling

- LLM とそれに対応したハイパラセットをサンプルすることで多様性を実現
- これに加えて code novelty rejection sampling を導入
    - LLM が変更可能なパートに対する embedding を作る
    - cosine similarity を計算 → 閾値を超えたら評価器 LLM にその変更が有意に新規かどうかを判定させる

**Method3: Execution and world feedback**

Multi-Objective Optimization & Textual Feedback

- これまでのステップ実行後のものとして、多目的評価を行う: スカラ値の適合度スコア r_i および public metrics, テキストでのフィードバック
    - これらのスコアは全てアーカイブに保存され、この後の生成に有用なコンテキスト情報として渡される

Adaptive LLM sampling evolution

- ざっくりいうと: 「どの LLM を使って、突然変異を作るか」を世代ごとに決め直す仕組み
- UCB1 という多腕バンディットアルゴリズムをベースにしているが、そのままだと LLM が作る突然変異の評価が不安定になりやすい
    - UCB1 では「各LLMが何回使われたかの visitation counter」と「これまでに得られた期待値の expected score」を使って、LLM の選択確率を計算する
- 安定性のために、以下の変更をShinkaEvolve では加える
    - 報酬定義の変更
        - 従来は突然変異プログラムの適合スコアをそのまま使う（絶対値）
        - 親プログラムをベースラインとして、どれくらいスコアが良くなったかの相対値を使う
    - 大胆さを促進
        - exp(・)とmax(・,0)の組み合わせにより、小さな改善がほぼ0に近い報酬地になり、大きな改善は指数関数的に大きくなる
    - スケールの違いを吸収
        - 各ドメインごとい適合スコアの範囲が違うので、観測した報酬統計量で相対スコアを正規化 → フィットネスが大きいドメインと、小さいドメインを同じ基準で比較できるようにする

Meta-Scratchpad & Online Refinement

- ShinkaEvolve では「成功プログラムの分析」を行う meta-scratchpad を導入して学習を促進
- T回の生成につき、各プログラムの評価を要約し、共通する最適化戦略を特定し、原理や原則を設計
- Meta-agent が行動可能な内容で洞察を生成し、突然変異プロンプトにこれを加える
    - 結構ガッツリした内容が吐き出される

Results

- **Circle packing: reproducing & improving AlphaEvolve Results**
    
    タスク概要
    
    - 26この円を正方形のフィールドに重なりなく並べ「半径の合計」を最大化する
    - 特徴
        - 配置（離散）と半径値（連続値）の両方を最適化する必要がある
        - 多数の局所最適解が存在するので、単純な方法では低品質な結果に収束しやすい
        - タスク意義: 進化的アルゴリズムなど、高度な探索戦略を試すのに適した難易度の高い問題
    
    SinkaEvolve’s Discovery Dynamics
    
    ![image.png](attachment:7ab0525f-3fe5-43df-849a-4c8fb87309d3:image.png)
    
    - 評価期間: 150 世代で実験: 従来手法が数千回のサンプルを必要とする中、わずか150回のサンプルで優れた性能を示した
    - 改善曲線 (fig5. left) から分かること = 3つのフェーズが存在
        1. 急速改善期: ベースとなる半径最適化戦略を発見
        2. 継続探索期: 制約ベースの高度手法が徐々に登場し、少しずつ改善
        3. 収束期: 最良の解について、restart しながら refine
    - 世代間の進化ツリー (fig.5 right) から分かること
        - 成功した innovation (green/yellow) が親になり、後の世代に伝播
        - 複数の枝が異なるアルゴリズムを探索 → 最終的に黒字のパスに収束
    
    ShinkaEvolve’s Discovered Solution
    
    - ShinkaEvolve の解には3つのイノベーションが含まれていた
        1. 構造初期化: 黄金比の螺旋パターンで角や辺に戦略的に円を配置
        2. ハイブリッド最適化: SLSQP (勾配ベース) と simulated annealing を組み合わせた全探索
        3. Intelligent な摂動: 局所移動とグローバルな円回転を交互に行って、局所最適解から脱却
        - そのほか、温度スケジューリングや制約を意識した半径計算、マルチレベルアプローチ（初期化→メタヒューリスティック探索→勾配ベースの仕上げ）などの工夫が観察された
- **AIME: Evolving Agent scaffolds for math reasoning**
    
    タスク概要
    
    - 競技用レベルの30個の数学的推論問題を用意
    - 制約: 計算効率の観点から、LLMに投げられるクエリは最大10回までとする
    - ベースモデルとして、gpt-4.1-nano を使って、75世代にわたり agent 設計を探索
    
    ShinkaEvolve’s Discovery Dynamics
    
    - 推論戦略・アンサンブル手法・検証技術を用いて、最適なエージェントアーキテクチャを特定
    - ベースライン: 人手構築された単純な単一クエリのエージェント / 多数決方式
    
    ![image.png](attachment:b66dd989-0c4e-4bc7-8424-05f36f039170:image.png)
    
    - 探索の結果、効率と性能の間にパレート境界を発見(fig.6 left)
        - 7回のLLMクエリで最大性能に到達した一方で、別のアーキテクチャでは10クエリで同等性能だった
    - 汎化実験により、AIME データセットについて以下の示唆が得られた (Fig. 6 mid)
        - 2023年版: 改善が小さい → データ汚染による飽和
        - 2025年版: 改善が大きい → 未知の問題に対する一般化
    - また、モデルを入れ替えて検証したところ、gpt-4.1-mini, gpt-4.1, o4-mini で転移が成功したことから、発見されたエージェントアーキテクチャがモデル固有の最適化ではなく、汎化されたものであることが示唆 (Fig. 6 right)
    
    ShinkaEvolve’s Discovered Solution
    
    - ShinkaEvolve で発見されたエージェント構成は次の通り
        - 3段階アーキテクチャ: 異なるペルソナを組み合わせた回答生成 / 批判的ピアレビュー / 統合
        1. 3つのペルソナ
            - 細かく逐次的に推論する系
            - 直感的なパターン認識系
            - アルゴリズム志向の数学者系
            - 各 experts は temp.=0.7 で推論
        2. 批判的ピアレビュー
            - temp.=0.1 で設定したレビュアーが各回答を厳しく検証
            - 複数の例でテストし、論理の欠陥を特定して修正を提案
        3. 回答の統合
            - temp.=0 で全ての解と批評を分析する統合役を投入
            - 最も信頼できるアプローチを選んで、標準的な解を構築
        - このプロセスによって「LLMコール10回まで」という制約を 3生成 + 3レビュー + 1統合の計7回に抑える
- **ALE-Bench: Evolving Programs for Combinatorial Optimization**
    
    タスク概要
    
    - AtCoder の問題10個からなる ALE-Bench LITE を使用
    - ALE-Agent という先行研究の LLM システムが発見した高性能の答えをベースラインに、これを改善できるかをテスト
    - 50回分生成をしてみた
    
    ShinkaEvolve’s Discovery Dynamics
    
    - 平均して 2.3% の改善を達成
        - ahc039 というタスクにおいては、AtCoder リーダーボード全体でも2位というスコアに
    - ただ改善案はアルゴリズム的にベースラインのものにかなり近いものにとどまった
    
    ShinkaEvolve’s Discovered Solution
    
    - ここでは ahc039 と ahc025 の2つの問題に焦点を当てて定性分析
    - ahc039
        - 課題: 与えられた制約のもと、イワシの数を減らしながらサバの数を最大化するような最適な軸揃えポリゴンを求めること
        - baseline の ALE-bench は kd-tree データ構造を使った焼きなまし法でスコア 2880 で5位
        - ShinkaEvolve は検証プロセスのキャッシュ化や近傍操作の改良などを導入することでスコア 3140 で2位まで改善
            - キャッシュ化: kd-tree にサブツリー統計 (Bbox や 魚の数) を書くノードにキャッシュ化する仕組みを追加
            - 近傍操作の改良: ターゲットエッジ移動という新しい手法を導入 → ご分類された魚 (ポリゴン外にいるサバ) をヒューリスティックに特定し、その状態を修正するために最も近い辺を貪欲的に移動させる
    - ahc025
        - 課題: 天秤を用いて任意の2つのアイテム集合の総重量を比較し、限られた回数の計量後にできるだけ等しい総重量を持つグループに分割する
        - baseline の ALE-Agent は焼きなまし法ベースの解法
        - キャッシュ処理の高速化、バックアップ用の重量推定の洗練、焼きなまし法をより焦点を絞った貪欲法と局所探索を組み合わせた最適化手法に置換
    - 上位の人間の解法との比較
        - 多くのタスクにおいてまだ改善の余地が大きい
        - また ALE-Agent のベースラインに近い探索が行われており、これは初期解への過学習の可能性が示唆される

**Discussion**

- Limitations
    - ShinkaEvolve では探索と活用のバランス調整の設定が fixed なもので、自由に調整しにくい → ドメインによってこのバランスは変わるはず
    - タスク仕様について、目的関数や評価の設計には人間による設計が必要
    - このフレームワークは「明確に数値的に評価できるタスク」に限定されている → 人文学的な答えの定まらない問題への適応が難しい
- Future Directions
    - LLM を使った自動タスク生成によるタスク仕様の自動化 → より高い自律性
    - システムが自ら objective を生成できるようにならないと、真のオープンエンドな展開は難しい
        - Self-referential な改善やメタ学習などがキーワード
