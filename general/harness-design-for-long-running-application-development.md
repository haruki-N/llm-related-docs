# Harness design for long-running application development を読む
- source: https://www.anthropic.com/engineering/harness-design-long-running-apps
- published: 2026/03/24
- Author: Prithvi Rajasekaran (Claudeのさらなる使い方を探求する [Labs](https://www.anthropic.com/news/introducing-anthropic-labs) というチームのメンバーっぽい)

**Harness design はエージェンティックコーディングのパフォーマンスのキーとなるもの。**
**この記事ではフロントエンドデザインおよび長時間の自律的ソフトウェアエンジニアリングにおいて、どのように Claude を押し上げたかを解説する。**

### Takeaways
1. **生成と評価の分離がハーネス設計の核心**: Sonnet 4.5 では自身の成果物を過大評価する傾向が顕著だった (Opus 4.5 は緩和したものの解決はしていない)。「自分に厳しくさせる」より「別のエージェントに懐疑的にレビューさせる」方が制御しやすく、改善サイクルも回しやすい
2. **主観的な品質も採点基準を与えれば段階評価できる**: 「良いデザインか？」ではなく「定義した原則に沿っているか？」と問うことで、一貫したフィードバックが可能になる。また評価基準のプロンプト自体がアウトプットの性格を直接形作る
3. **Planner はハイレベルに留めるべき**: 詳細な技術仕様まで踏み込むと、誤りが実装フェーズに連鎖する。「何を作るか」の制約を与えるに留め、実装の詳細は generator に委ねる
4. **ハーネスの各要素は「そのモデル単体ではできないこと」を補完するもの**: Sonnet 4.5 では context anxiety 対策として context reset が不可欠だったが、Opus 4.6 ではその問題自体が解消され、スプリント分割や per-sprint 評価も不要になった。新モデルのリリース = ハーネス設計の見直しタイミング
5. **ハーネスの組み合わせ空間は縮小ではなく遷移する**: Opus 4.6 で足場を減らせた一方、「アプリ操作用エージェントを generator に構築させる」など新たな組み合わせが生まれた。AI エンジニアの仕事は「次の組み合わせ」の探求にある

---

- 過去数ヶ月に渡り、互いに関係する2つの問題に取り組んでいた
  1. Claude に高品質なフロントエンドデザインを作らせること
  2. 人間の介入なしに完全なアプリケーションを構築させること
  - この取り組みは [frontend design skill](https://github.com/anthropics/claude-code/blob/main/plugins/frontend-design/skills/frontend-design/SKILL.md) と [long-running coding agent harness](https://www.anthropic.com/engineering/effective-harnesses-for-long-running-agents) という投稿にもあるように、以前から取り組まれていた。プロンプトエンジニアリングとハーネス設計でベースラインより大きく性能を伸ばせたが、いずれも最終的には限界に突き当たった

- 上記状況打破のため、2つの異なるドメイン (主観的な好みによって定義されるものと定量化可能な正確性およびユーザビリティ) に跨る新しいアプローチを試した
  - GAN にインスピレーションを受け、`generator` と `evaluator` からなるマルチエージェントアーキを考えた
  - 特に `evaluator` は具体的かつ段階評価可能な指標を持つことで "is this design good?" のような主観評価も可能になるように設計
  - 先行していた取り組みから、ハーネスの取り付けかたとして「ビルドを扱いやすいチャンクに分割すること」「構造化されたアーティファクト（成果物ファイル）を使って、セッションを跨いでコンテキストを引き継げるようにすること」を学んでいたので、これらも活用
    - したがって最終的には上記の2つのエージェントだけでなく、`planner` のエージェントも加えた3体の構造を取ることで、長時間・フルスタック・高品質な自律コーディングを実現した

## 1. Why naive implementations fall short
- これまでの取り組みから、ハーネス設計は長時間の自律コーディングに本質的に効いてくるものだとわかっていた。先の実験では以下を試した：
  - `Initializer agent`: product spec をタスクリストに変換する
  - `Coding agent`: セッションを跨がず、一度に1つの機能を実装する
  - この構成は開発者コミュニティでも試されていて、["Ralph Wiggum"](https://ghuntley.com/ralph/) メソッドとして hooks やスクリプトを使ってイテレーションサイクルを回すように作られるものもあった
- ただこの方法だと、複雑なタスクはエージェントがレールから外れやすいなどの欠点があった。問題を分解していく中で、このような失敗には2つの共通した要素があることを発見した
  1. コンテキストウィンドウがいっぱいになるにつれ、エージェントは一貫性を失いやすい
     - 一部のモデルでは Context anxiety (コンテキスト上限に近づいているとモデルが感じたタイミングで、終わるべきでないタスクを早めに締めようとする問題) などが見られた: コンテキストを完全にクリアし、新しいエージェントを起動した上で前のエージェントの状態および次のステップを含む構造化されたハンドオフの組み合わせからなる context reset は上記の問題を改善できる
     - Context reset は compaction とは異なる: Compaction は同じエージェントが短い要約を使って処理を続けられるよう、実行履歴の前半部分を要約し続けるもの。連続性を担保できるが「まっさらな状態」をエージェントに与えられないため、context anxiety は残り得る。
       - Claude Sonnet 4.5 ではこの context anxiety が強く表れることが観察されていたので、**compaction だけでは長時間タスクで十分な性能を引き出せず、context reset がハーネス設計において不可欠になった**: ただその分オーケストレーションの複雑さ、トークンのオーバーヘッド、各ハーネス実行あたりのレイテンシを増加させることになる。
  2. 高すぎる自己評価
     - 人間には平凡に見える成果物も、エージェントは往々にして自身の成果物を高く自己評価する傾向があった
     - この傾向はテスタブルでない、デザインのような主観タスクで特に顕著だった
     - ただ、テスタブルなタスクであっても、上記のような歪んだ傾向は生じうるため、「作業をするエージェント」と「それを評価するエージェント」を分離することが重要になる
       - `Evaluator` も LLM であるため、本質的な解決ではないが「自分の仕事に厳しくさせる」よりも「懐疑的にレビューさせる」方がまだコントロールしやすいため、問題の緩和に繋げられる構成となる
       - また外部評価としてのフィードバックループが存在することで、作業者である `generator` もそれを足場にして具体的な改善サイクルを回しやすくなる

## 2. Frontend desing: making subjective quality gradable
- section1 で語った自己評価問題が最も顕著に表れるフロントエンドのデザインタスクで実験を始めた
  - 人間の仲介なしでは、Claude は安全かつ予測可能な、いわゆる平凡なタスクに終始する
- フロントエンドデザイン用のハーネスを作る上で、2つの洞察で方向性を決めた
  1. 美的感覚は完全にスコア化することはできず、個人の好みも千差万別ではあるものの、デザイン原則や好みをコード化した採点基準を用意することで改善可能になる
    - 「このデザインは美しい？」に一貫して答えることは難しいが、「私たちのデザイン原則にあっている？」なら一貫して答えられる
  2. フロントエンドの生成とフロントエンドの採点を分類して、改善フィードバックループを作れる

- `generator` および `evaluator` の両方に対して以下の評価基準を与えた
  - **Design quality**: パーツの寄せ集めではなく、デザイン全体に一貫性があると感じられる？色・タイポグラフィ・レイアウト・画像・そのほかの細部が組み合わさって、はっきりしたムードやアイデンティティを形作られている場合は高評価となる。
  - **Originality**: 独自な判断や工夫の跡が見られる？テンプレートレイアウトやライブラリのデフォルト、よくある AI-generated なデザインにとどまっていない？人間のデザイナーが「意図的なクリエイティブ選択がある」と感じられることが重要で、いかにも AI-slop なデザインは減点となる。
  - **Craft**: 技術的に作り込んだ完成度の高いものになっている？タイポグラフィの階層、余白の一貫性、色の調和、コントラスト比などが評価対象。創造性よりも「ちゃんと作り込まれているか」のチェックで、妥当な実装であれば多くは合格する基準点。
  - **Functionality**: 見た目とは独立した使いやすさで、ユーザーはそのインターフェースを直感的に理解し、操作に迷わないかを評価する。

- Craft や Functionality と比べると、Design quality と Originality の方が重要になる
  - 前者はClaudeは得意で、後者は良くても平凡という感じ
  - `evaluator` は few-shot 付きのルーブリックを使ってキャリブレーションを実施

- 改善ループの実装
  - Claude Agent SDK で実装し、`generator`はプロンプトに基づいて HTML/CSS/JS のフロントエンドを生成。`evaluator` には Playwright MCP を与え、スコアリングと詳細なレビューを書くように指示
    - 1回の生成につき、5-15回のイテレーションを回した。Playwright MCP での実際の操作などがあったので、フルの実行は最大で4時間程度を要した
      - 評価を回すごとに採点は改善し、その後頭打ちする傾向が見られた
      - またフィードバックの内容は、想像以上に `generator` の方向性を決定した: 「最高のデザインは美術館に展示できるクオリティである」といったフレーズを含めたことで、デザインが特定の見た目に収束するなどの現象があった → 評価基準に紐づいたプロンプト自体が、アウトプットの性格を直接形作っていることを示唆している
    - `generator` はレビュー結果に基づき、スコアがよければその方向性を磨き込み、うまくいっていなければアプローチをまるっとピボットさせるように動かした

## 3. Scalling to full-stack coding
- フロントエンドデザインでうまくいった仕組みを、フルスタック開発にも適用する
- アーキテクチャ
  - 前日譚的に試していたのは次の構成: `inintializer agnent + coding agent + Sonnet4.5 + context reset`
    - ただ、Opus 4.5 では context anxiety の問題が解決されつつあったため、今回は context reset をハーネス設計から除外した: 代わりに auto compaction を利用
  - 先述の通り、3つのエージェントを組み合わせた構成を取る

> **Planner**
> - 以前までのハーネスだと、ユーザーが最初に詳細な仕様書を用意する必要があったが、これを自動化
> - 1-4行程度のシンプルなプロンプトを受け取り、それを完全なプロダクト仕様に昇華させるのが planner の役割
> - 技術実装の詳細ではなう、プロダクトの背景文脈とハイレベルな技術設計にフォーカス
>   - 詳細を決めようとしてどこかにミスが紛れると、後段の実装フェーズに連鎖する懸念があったので、「どんな成果物を出すべきか」という制約を与えるにとどめた

> **Generator**
> - 1実行につき1つの機能実装のこれまでのアプローチはスコープの管理のしやすさはあった
> - ここでも似たアプローチとして「スペックからタスクを1つピックアップしてスプリント形式で実装させる」というアプローチをとった
> - `evaluator` のレビュー前に、スプリントで実装した内容を self-review させるように指示を出して refine

> **Evaluator**
> - 先行検証時のものもだいぶワークしていたが、実際に使おうとするとバグがあるみたいな事態は避けられない
> - この部分も自動サイクルに含めるべく、Playwright MCPを組み合わせて UI/UX, API エンドポイント動作、データベース状態などもテストできるようにした
> - 発見されたバグやプロダクトの機能性・デザイン性、コード品質などを総合的に定量評価
>   - チェック項目の評価基準は厳しく、いずれかの項目1つでも落ちるとそのスプリントは全体的にやり直しになる（この際、`evaluator` からは詳細なフィードバックが提供される）

- 各スプリントの前に、`generator` と `evaluator` は「スプリント契約」として合意をとる
  - そのスプリントにおいて「何が完了とみなされるか」をコードを書く前に合意形成する: `planner` の仕様をハイレベルに留めていたので、ユーザーストリートテスト可能な実装のギャップをここで埋める
  - `generator` は何を作るか、どうなっていれば成功とみなせるかを提案し、`evaluator` はその提案をレビューして正しいものを作ろうとしているのかを確認する: 両者が同意に至るまでくり返す
  - エージェント間のコミュニケーションはファイル経由で行われた。このようにすることで合意形成のイテレーションも回しやすく、その後の実装やQAにも合意内容を引き継ぎやすくなる

## 4. Running the harness
- ハーネスの初版では Opus 4.5 を使い、ハーネスの有無でどう振る舞いが変化するかを検証した
- お題: _Create a 2D retro game maker with features including a level editor, sprite editor, entity behaviors, and a plyaable test mode._
- ハーネスなしとありを比べると、タスク時間は 20min から 6hours に伸び、コストも $9 から $200 分の稼働となった
- この伸びの分、最終的な成果物のしつも明確に異なるクオリティに
  - 見た目もさることながら、機能性における完成度などハーネスの威力を感じられる仕上がりに
- 具体的な仕上がり内容や注目どころは元記事参照: https://www.anthropic.com/engineering/harness-design-long-running-apps#:~:text=implementation%20too%20early.-,Running%20the%20harness,-For%20the%20first

## 5. Iterating on the harness
- 検証したハーネスの性能は良いことがわかったが「重くて遅くて高コスト」という問題があった
- Next step としてパフォーマンス低下せずにハーネスを簡素化するというもの設定
  - 前提として「ハーネスの各要素はモデル単体ではできないことを補完する」というのを置いた設計にすべき
  - 従ってモデル性能の向上に伴って、この仮定は定期的に疑う必要がある: 当時は有効だった足場 (scaffolding) が過剰になる・ワークしなくなる可能性がある
  - [Building Effective Agents](https://www.anthropic.com/research/building-effective-agents) のポストでも _"find the simplest solution possible, and only increase complexity when needed"_ という原則を敷いている
- ちょうどこの再検討タイミングで Opus 4.6 がリリースされ、「長時間のプランニングがうまい」「大きなコードベースでも安定して動ける」「自己デバッグ・コードレビューが強い」「長コンテキストでの情報管理が向上」といった能力が押し出され、まさに以前ハーネスが補完していた部分をモデル自身が自立できるようになっている

## 6. Removing the sprint construct
- Opus 4.6 ならスプリントレベルにタスクを decompose する部分を自分でうまくやれると判断: section 3 で言及していた `generator` と `evaluator` による「スプリント契約」のプロセスを排除
- ただし、`planner` と `evaluator` はそれぞれ残す
  - `planner` がないと、`generator` は仕様をきちんと作らずにスコープを小さく見積りすぎる
  - `evaluator` はスプリントごとに挟むのではなく、タスク全体が完了したタイミングで発動させる形にした
    - モデルの自己デバッグ性能向上などに起因し、「タスクがモデル単体で安定してこなせる範囲の内側か外側か」によって `evaluator` の有用性が変化した: Opus 4.6 ではこの境界線がグッと外側に押し広げられたため、細かすぎる評価は余計なオーバーヘッドに
  - この簡素化に加え、`generator` に対して「アプリ自身の機能をツール経由で操作できる適当なエージェントを構築させる」ようにプロンプトを追加
    - この辺りの知識は比較的最近のもので、Claude の学習データではカバーが薄い: かなりの試行錯誤を要したが、十分にチューニングすることで正しくエージェントを構築できるようになった

## 7. Results from the updated harness
- 簡素化したハーネスを検証するため、作曲・録音・曲のミキシングが可能な Digital Audio Workstation (DAW) を生成させた
- お題: _Build a fully featured DAW in the browser using the Web Audio API_
- `Planner` + `Build-QA` x 3 round 分の実行: 時間にして4時間ほどで $124 のコスト
  - `Generator` を Opus 4.5 にしても、長時間実装時は抜けがあり、機能的なギャップなどをうまく `evaluator` が指摘できていた
- 最終成果物はプロダクションレベルには遠く及ばないまでも、それなりに動いた
  - DAW でどんな音が鳴っているかをモデルは知覚できないので、QA のフィードバックも難しい部分があったと考えられる
  - ただ、必要なコア機能は全て実装されており、それらの機能を組み合わせて短い楽曲を作ることができた

## 8. What comes next
- モデルの発達を軸に、ハーネスの設計やその有用性は変化する
- 今回の一連の取り組みから見出せる教訓
  - モデルを常に試し、望むアウトカムを得るには何がギャップかを考えることが大事
  - モデルがリリースされたタイミング = 設計したハーネスを見直すタイミング: 新しいモデルだからこそ可能になった能力を実現するためにパーツを足していく
- この取り組みから筆者が強く感じるのは「ハーネスの組み合わせ空間は縮小するのではなく、遷移していくもの」
- AI エンジニアにとっての面白い仕事は常に「次の新しい組み合わせ」を探求し続けるところにある
